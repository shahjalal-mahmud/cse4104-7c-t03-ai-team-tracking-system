# 02 – Functional Requirements

**How to read this file.** Each requirement is one testable statement. **Phase** 1 = Must (build first), Phase 2 = Should (build after Phase 1). Requirement IDs are numbered serially inside each group.

## 3.1 Authentication and Account Management (AUTH)

| FR-AUTH-02 | The system rejects a duplicate email, student ID or GitHub username (case-insensitive for email and username) with the distinct codes `EMAIL_TAKEN`, `STUDENT_ID_TAKEN`, `GITHUB_USERNAME_TAKEN` (HTTP 409).                                                                                                                                                                                                                  | Must   | 1   |

## 3.2 Team Management (TEAM)

The student becomes the Team Leader with `projectRole` = `Team Leader`. Only users with role `student` can create teams. Creation is rejected with `ALREADY_IN_TEAM` if the student already belongs to a team in the course offering. The `repositoryUrl` must be a valid `github.com` repository URL (`INVALID_REPOSITORY_URL`), and the server verifies with GitHub that the repository exists and is public before the team is created (`REPOSITORY_UNREACHABLE`, `GITHUB_RATE_LIMITED`).                                                                                                                         | Must   | 1   |

| FR-TEAM-04 | The Team Leader can add a member by `studentId` and `projectRole` (free text, 2–60 characters). The member is added immediately, with no acceptance step. | FR-TEAM-06 | An Instructor can list and view any team (details, members, repository, submissions and metrics) but cannot edit a team, add or remove members, change the leader, or delete or deactivate a team. | FR-TEAM-07 | The Instructor sets the allowed sections, the team name pattern, the minimum team size (`min_team_size`), the maximum team size (`max_team_size`; defaults 2 and 6, with `1 <= min_team_size <= max_team_size <= 10`) and the registration code in course settings.                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | Should | 2   |

| FR-TEAM-09 | A team with fewer than `min_team_size` members may exist (a new team starts with only its leader) but cannot submit a milestone (`TEAM_TOO_SMALL`). Changing the size limits never removes members from existing teams; the new limits apply to later add-member and submit actions.                                                                                                                                                                                                                                                                                                                                                                                                                                                             | Must   | 1   |
| FR-TEAM-10 | The Team Leader can edit `projectTitle` at any time.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             | Must   | 1   |
| FR-TEAM-11 | The team's `repositoryUrl` is provided at team creation, stored in canonical form (`https://github.com/{owner}/{name}` with the owner and name as GitHub returns them) together with `repo_owner` and `repo_name`, and can **never be changed** afterwards, by the Team Leader or by an Instructor (`REPOSITORY_LOCKED`). The same repository cannot be registered by two teams in one offering, compared case-insensitively (`REPOSITORY_IN_USE`).                                                                                                                                                                                                                                                                                              | Must   | 1   |
| FR-TEAM-12 | The Team Leader can remove a non-leader member. The leader cannot remove themself (`CANNOT_REMOVE_LEADER`). Only the current leader can do this (`NOT_TEAM_LEADER`), and the new leader must already be a member (`VALIDATION_ERROR` on field `userId` otherwise).                                                                                                                                                                                                                                                                                                                                                                                                               | Must   | 1   |
| FR-TEAM-14 | Any member of a team can view the team's details and member list (names, student IDs, GitHub usernames, project roles).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | Must   | 1   |

## 3.5 Submission Validation (VAL)

All checks below are **blocking** and run synchronously inside the submit request, **before** anything is stored. If any check fails, the request is rejected with HTTP 422 and nothing is stored. If GitHub cannot be reached at that moment, the check fails and the leader may try again later.

| ID        | Requirement                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             | Pri    | Ph  |
| --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------ | --- |
| FR-VAL-01 | `required_fields`: all required documents of the milestone are present and non-empty, and, when the milestone requires a live URL, `liveUrl` is present and is a well-formed `http` or `https` URL of at most 2,000 characters (`VALIDATION_ERROR`).                                                                                                                                                                                                                                                                    | Must   | 1   |
| FR-VAL-02 | `team_name_format`: the team name matches the course `team_name_pattern`.                                                                                                                                                                                                                                                                                                                                                                                                                                               | Must   | 1   |
| FR-VAL-03 | `file_names`: every uploaded file name equals its pattern with `{TEAM}` replaced by the team name, compared case-sensitively (example `{TEAM}_Proposal.pdf` → `CSE4104-7C-T03_Proposal.pdf`) (`FILENAME_MISMATCH`).                                                                                                                                                                                                                                                                                                     | Must   | 1   |
| FR-VAL-04 | `file_types`: the file extension is `pdf` or `docx`, equals the extension of the requirement's pattern, and the real content type matches it (`INVALID_FILE_TYPE`).                                                                                                                                                                                                                                                                                                                                                     | Must   | 1   |
| FR-VAL-05 | `file_sizes`: every file is at most 10 MB (`FILE_TOO_LARGE`). A file above the upload limit is rejected by the upload middleware with the same code.                                                                                                                                                                                                                                                                                                                                                                    | Must   | 1   |
| FR-VAL-06 | `repository_accessible`: the GitHub API returns the team's repository (HTTP 200) and it is not private (`REPOSITORY_UNREACHABLE`; `GITHUB_RATE_LIMITED` if GitHub rate limits the request).                                                                                                                                                                                                                                                                                                                             | Must   | 1   |
| FR-VAL-07 | `live_url`: in Phase 1 this check only confirms that the live URL is well-formed when the milestone requires one (status `passed`), and is `skipped` otherwise.                                                                                                                                                                                                                                                                                                                                                         | Must   | 1   |
| FR-VAL-08 | Every check keeps its own result: one row per check with `status` (`passed`, `failed`, `skipped`, `error`) and a message. The report is returned in the response (including a rejected request), stored with every successful submission, and shown to the team and the Instructor.                                                                                                                                                                                                                                     | Must   | 1   |
| FR-VAL-09 | Live URL reachability: an HTTP GET to the live URL returns a final 2xx status within 10 seconds (one retry after 3 seconds on timeout); the result stores final status, redirect count and response time in ms (`LIVE_URL_UNREACHABLE`). Only `http` and `https` URLs on ports 80 and 443 are accepted, the host is resolved first, and private, loopback and link-local addresses are refused, including after each redirect (SSRF protection). A refused URL gives status `failed` with message `URL is not allowed.` | Should | 2   |

## 3.6 GitHub Integration and Contribution Metrics (GH)

| ID       | Requirement                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       | Pri  | Ph  |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---- | --- |
| FR-GH-01 | A sync fetches the commits of all branches of the team's repository. The system uses read-only access and never writes to GitHub.                                                                                                                                                                                                                                                                                                                                                                                                 | Must | 1   |
| FR-GH-02 | For each commit the system stores SHA, author login, author name, author email, authored date, committed date, message, additions, deletions, files changed, merge flag, bot flag, branches and URL.                                                                                                                                                                                                                                                                                                                              | Must | 1   |
| FR-GH-03 | Commits are matched to members in this order: (1) the commit's GitHub author login equals the member's `github_username` (case-insensitive); (2) the commit author email equals the member's registered email (case-insensitive); (3) the commit author email is a GitHub noreply address (`{id}+{username}@users.noreply.github.com` or `{username}@users.noreply.github.com`) with `username` equal to the member's `github_username`. Unmatched commits are stored with `member_user_id = null` and displayed as "Unassigned". | Must | 1   |
| FR-GH-04 | The analysis period for a milestone starts at the deadline of the published milestone with the next lower `weekNumber`, otherwise at the offering `start_date` 00:00 Asia/Dhaka. It ends at the milestone deadline, or at the submission time if the submission exists and is later. The all-time period runs from the offering `start_date` 00:00 Asia/Dhaka until now. Days and weeks are calculated in Asia/Dhaka (weeks start on Monday); all timestamps are stored in UTC.                                                   | Must | 1   |
| FR-GH-05 | The system calculates per member and per team for a period: commits, active days, additions, deletions, files changed, share of counted commits (denominator: all counted commits of the team, including Unassigned), first and last commit time, and per-week commits and lines changed. Metrics are calculated from commit metadata only and are never presented as a definitive measure of individual effort or quality.                                                                                                       | Must | 1   |
| FR-GH-06 | Merge commits (more than one parent) and bot commits (author login ending in `[bot]` or GitHub user type `Bot`) are excluded from metrics according to the course settings `excludeMergeCommits` and `excludeBotCommits` (both default true). Excluded commits remain stored. "Counted" commits are stored commits inside the period that are not excluded.                                                                                                                                                                       | Must | 1   |
| FR-GH-07 | Stored commits are never re-fetched in detail: a sync fetches the commit list for each branch (only commits since the offering start date) and fetches details only for SHAs not yet stored.                                                                                                                                                                                                                                                                                                                                      | Must | 1   |
| FR-GH-08 | A manual sync is refused with `SYNC_COOLDOWN` if the team's last sync finished less than 5 minutes ago. A submission-triggered sync ignores the cooldown. Only one sync per team can run at a time (`SYNC_IN_PROGRESS`). A sync keeps the newest 2,000 distinct commits across all branches; if more exist the sync completes with `truncated = true`.                                                                                                                                                                            | Must | 1   |
| FR-GH-09 | Every sync is recorded in `github_sync_runs` with status `queued`, `running`, `completed` or `failed`. The API starts a sync with HTTP 202 and the UI polls the run. On server start, every run in `queued` or `running` is set to `failed` with error code `INTERRUPTED`, regardless of age.                                                                                                                                                                                                                                     | Must | 1   |
| FR-GH-10 | GitHub errors (404 `GITHUB_REPO_NOT_FOUND`, 403 rate limit `GITHUB_RATE_LIMITED`, 5xx, network) are caught, stored on the sync run with a code and message, and shown to users. Commits are stored in batches, so a failed run keeps the commits it already stored; stored commits are never deleted and unrelated features keep working.                                                                                                                                                                                         | Must | 1   |
| FR-GH-11 | Only public repositories on `github.com` are supported.                                                                                                                                                                                                                                                                                                                                                                                                                                                                           | Must | 1   |
| FR-GH-12 | Commit attribution is recomputed (no GitHub call) when a member is added or removed. It is also recomputed when a member's `github_username` changes (this part ships with FR-AUTH-09).                                                                                                                                                                                                                                                                                                                                           | Must | 1   |

## 3.7 AI Review Engine (AI)

The exact AI input, commit reference scheme, output schema and prompt are in `09-ai-integration-spec.md`.

| ID       | Requirement                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | Pri  | Ph  |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---- | --- |
| FR-AI-01 | The system builds the Gemini request from anonymised commit metadata, computed metrics and the milestone title and guidelines, using a fixed prompt version and a fixed set of input fields.                                                                                                                                                                                                                                                                                                                             | Must | 1   |
| FR-AI-02 | Before sending, member names, GitHub usernames and emails are replaced by labels (`Member A`, `Member B`, ...). Unmatched authors are labelled `Unassigned Author 1`, `Unassigned Author 2`, ... Any occurrence of a member's name, username or email inside a commit message is replaced by that member's label. Commit messages and guidelines are sanitised (first line only, URLs, emails and path-like text removed). Source code, file contents, file paths, diffs, repository URLs and team names are never sent. | Must | 1   |
| FR-AI-03 | Gemini is asked for JSON only, following a fixed output schema. Commits are sent with short refs (`c1`, `c2`, ...) instead of SHAs, and the response cites refs.                                                                                                                                                                                                                                                                                                                                                         | Must | 1   |
| FR-AI-04 | The response is validated against the schema. On invalid output the system retries once with the validation error appended; after that the report is `failed` with `AI_INVALID_OUTPUT`. Network, timeout, 429 and 5xx errors are retried with backoff.                                                                                                                                                                                                                                                                   | Must | 1   |
| FR-AI-05 | Every AI flag cites at least one commit ref that exists in the input that was sent; refs are mapped back to SHAs; flags that fail are dropped and counted in `result.droppedFlagCount`.                                                                                                                                                                                                                                                                                                                                  | Must | 1   |
| FR-AI-06 | Labels are mapped back to real names only when the Instructor views the report. The mapping (`label_map`) stores user IDs, not names.                                                                                                                                                                                                                                                                                                                                                                                    | Must | 1   |
| FR-AI-07 | Each report stores `model`, `prompt_version`, `input_hash` (SHA-256 of the exact request body), token counts, timestamps and the validated result.                                                                                                                                                                                                                                                                                                                                                                       | Must | 1   |
| FR-AI-08 | Only an Instructor can request a review. The Instructor can request a new review at any time; each request creates a new report row and earlier reports are kept.                                                                                                                                                                                                                                                                                                                                                        | Must | 1   |
| FR-AI-09 | A review requires at least one counted commit in the period (`NO_COMMIT_DATA`). Only one review can be pending per submission (`AI_REVIEW_IN_PROGRESS`). An Instructor can make at most 10 review requests per hour (`RATE_LIMITED`). At most the newest 400 commits in the period are sent.                                                                                                                                                                                                                             | Must | 1   |
| FR-AI-10 | AI output is advisory: all AI content is labelled with an advisory banner, it can never create, change, approve or publish a grade, and it can never change a submission status except to `ai_reviewed`. Students never see AI reports or AI flags.                                                                                                                                                                                                                                                                      | Must | 1   |
| FR-AI-11 | An Instructor can dismiss an AI report; a dismissed report stays stored, is hidden by default and does not count for `ai_reviewed` status.                                                                                                                                                                                                                                                                                                                                                                               | Must | 1   |
| FR-AI-12 | A failure or rate limit of Gemini never deletes stored data and never blocks unrelated features. The failure is recorded on the AI report (`AI_UNAVAILABLE`) and shown to the user.                                                                                                                                                                                                                                                                                                                                      | Must | 1   |
