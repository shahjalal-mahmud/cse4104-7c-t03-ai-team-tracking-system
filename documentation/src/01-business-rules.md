# 01 – Business Rules

Every rule below is enforced **on the server**. "Enforced at" shows the layer that must implement it (`API` = service/validator, `DB` = constraint or index, `UI` = convenience check that never replaces the server check).

Rule IDs are numbered serially from BR-01 to BR-39 in order of appearance. Section 9 holds every numeric limit in one table.

---

## 1. Teams and membership

| ID    | Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | Enforced at | Error code                                                                                                                     |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- | ------------------------------------------------------------------------------------------------------------------------------ |
| BR-01 | **Team naming and numbering.** A team name is generated as `{course_code}-{section}-T{NN}` (example `CSE4104-7C-T03`). `section` is chosen by the creating student and must be one of the course's `allowed_sections` (default `7A`, `7B`, `7C`); any other section is a validation error on field `section`. `NN` is **assigned automatically by the server**, serially per course offering and per section: the first team in a section gets `01`, the next `02`, and so on, zero-padded to two digits (maximum 99). The server computes it inside the team-creation transaction as the highest existing number for that offering and section plus 1, after locking the course offering row (`SELECT ... FOR UPDATE`). Teams are never deleted, so numbers are never reused. A unique constraint on offering + section + number is the safety net. The student cannot choose or edit `NN`. The final name must match the course's `team_name_pattern` (default `^CSE4104-[0-9][A-Z]-T[0-9]{2}$`) and be unique within the offering. | API, DB     | `VALIDATION_ERROR`, `INVALID_TEAM_NAME`, `TEAM_NAME_TAKEN`, `TEAM_LIMIT_REACHED`                                               |
| BR-02 | **Membership and team size.** A team has exactly one Team Leader. A student belongs to at most one team per course offering. The Instructor sets `min_team_size` and `max_team_size` in course settings (defaults 2 and 6; `1 <= min_team_size <= max_team_size <= 10`). A team has at most `max_team_size` members including the leader; adding a member beyond the maximum is rejected. A team with fewer than `min_team_size` members may exist (a new team starts with only its leader) but cannot submit a milestone (BR-13). Changing the limits never removes members from existing teams; the new limits apply to later add-member and submit actions.                                                                                                                                                                                                                                                                                                                                                                        | API, DB     | `ALREADY_IN_TEAM`, `TEAM_FULL`, `TEAM_TOO_SMALL`                                                                               |
| BR-03 | **Team creation.** The authenticated student who creates a team becomes its Team Leader. The student chooses the section and provides the team's repository URL; the server verifies the repository (BR-06, BR-20) **before** the transaction starts, then generates the team number (BR-01) and creates the team and the leader's membership in one transaction. Creation is rejected if the student already belongs to a team in the offering. Only users with role `student` can create teams.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     | API         | `ALREADY_IN_TEAM`, `FORBIDDEN`, `INVALID_REPOSITORY_URL`, `REPOSITORY_UNREACHABLE`, `REPOSITORY_IN_USE`, `GITHUB_RATE_LIMITED` |
| BR-04 | **Member eligibility.** A member is identified by a registered student ID (11 digits). The Team Leader adds members by student ID; the member is added immediately, with no acceptance step. The system rejects an unknown student ID and a student already in a team in the same offering.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           | API         | `STUDENT_NOT_FOUND`, `ALREADY_IN_TEAM`                                                                                         |
| BR-05 | **Leader and member changes.** The Team Leader can remove non-leader members. The leader cannot remove themself. The leader can **transfer leadership** to any current member of the same team; the new leader must already be a member (otherwise validation error on field `userId`), and the previous leader becomes a regular member. There is exactly one leader at all times. Instructors cannot change team membership or leadership.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | API         | `CANNOT_REMOVE_LEADER`, `NOT_TEAM_LEADER`, `VALIDATION_ERROR`                                                                  |
| BR-06 | **Repository URL: verified, canonical, unique, permanent.** A team has one `repository_url`, provided at creation. The server parses it with the pattern in BR-20, calls the GitHub API for it, and accepts it only if GitHub returns the repository and reports it as **not private**. The stored URL is the canonical form `https://github.com/{owner}/{name}` using the owner and name exactly as GitHub returns them (no `.git`, no trailing slash). Owner and name are compared case-insensitively everywhere. The same repository cannot be registered by two teams in one offering. After creation the URL can **never be changed**, by the Team Leader or by an Instructor.                                                                                                                                                                                                                                                                                                                                                   | API, DB     | `INVALID_REPOSITORY_URL`, `REPOSITORY_UNREACHABLE`, `REPOSITORY_IN_USE`, `REPOSITORY_LOCKED`                                   |

## 2. Milestones and rubrics

| ID    | Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | Enforced at | Error code                                    |
| ----- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- | --------------------------------------------- |
| BR-07 | **Milestone availability.** A milestone is visible to students and open for submission only when its status is `published`. A milestone can be deleted only if it is `draft` or has no submissions.                                                                                                                                                                                                                                                                                                                           | API         | `MILESTONE_NOT_PUBLISHED`, `MILESTONE_LOCKED` |
| BR-08 | **Milestone lock after first submission.** Once any submission exists, only `title`, `description`, `guidelines` and `deadline` may be edited. `weekNumber`, `maxMarks`, `requireLiveUrl`, document requirements and rubric criteria are locked. A milestone with submissions cannot be unpublished.                                                                                                                                                                                                                          | API         | `MILESTONE_LOCKED`                            |
| BR-09 | **Publish preconditions and deadline order.** A milestone can be published only if: it has at least one rubric criterion; the sum of all criterion `maxPoints` equals `maxMarks`; the deadline is in the future at the time of publishing; and its deadline is later than the deadline of every published milestone with a lower `weekNumber` and earlier than the deadline of every published milestone with a higher `weekNumber`. The same deadline-order check runs when the deadline of a published milestone is edited. | API         | `RUBRIC_TOTAL_MISMATCH`, `VALIDATION_ERROR`   |
| BR-10 | **Week uniqueness.** `weekNumber` (1 to 14) is unique per course offering.                                                                                                                                                                                                                                                                                                                                                                                                                                                    | API, DB     | `MILESTONE_WEEK_TAKEN`                        |

## 3. Submissions

| ID    | Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            | Enforced at | Error code                                                                                                                                              |
| ----- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| BR-11 | **Submission authority.** Only the Team Leader of the team may create the submission. Other members have read-only access. An Instructor can never submit a milestone on behalf of a team.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | API         | `NOT_TEAM_LEADER`                                                                                                                                       |
| BR-12 | **Deadline handling.** The server captures `receivedAt` (the current time) as the first step of the submit request, before any validation or upload. `receivedAt` is stored as `submitted_at` and compared with the milestone deadline. A submission received after the deadline is **accepted** (if it passes BR-14) and marked `is_late = true`. There is no cut-off and no automatic mark penalty; the Instructor decides manually.                                                                                                                                                                                                                                                                                                                                                                          | API         | –                                                                                                                                                       |
| BR-13 | **Single submission, no resubmission.** A team can create **exactly one submission per milestone**, and it has exactly one version. Resubmission, replacement and editing of a stored submission are not allowed, by anyone. A submission is allowed only if: the milestone is `published`; the team has no submission for this milestone yet; the team has at least `min_team_size` members (BR-02); and the submission passes the validation of BR-14 and BR-15. A submission that fails any check is rejected and **nothing is stored**. If two requests race, the database unique constraint decides and the loser receives `SUBMISSION_EXISTS`. A successful first submission triggers a GitHub sync (BR-21).                                                                                              | API, DB     | `SUBMISSION_EXISTS`, `MILESTONE_NOT_PUBLISHED`, `TEAM_TOO_SMALL`, `VALIDATION_ERROR`                                                                    |
| BR-14 | **Mandatory validation.** There is no submission without validation. Validation runs synchronously inside the submit request, **before** anything is stored, and every check is blocking. If any check fails, the request is rejected with HTTP 422 and nothing is stored. Checks, in order: required fields present (including a well-formed `http` or `https` live URL when the milestone requires one); team name matches `team_name_pattern`; document file names equal the milestone pattern; file extension and real content type allowed; file size within limit; repository reachable on GitHub and public; live URL reachable (Phase 2). If GitHub cannot be reached at that moment, the check fails and the leader may try again later. Every check keeps its own result and message in the response. | API         | `VALIDATION_ERROR`, `FILENAME_MISMATCH`, `INVALID_FILE_TYPE`, `FILE_TOO_LARGE`, `REPOSITORY_UNREACHABLE`, `LIVE_URL_UNREACHABLE`, `GITHUB_RATE_LIMITED` |
| BR-15 | **File constraints.** Each milestone defines its required documents (key, label, filename pattern). Allowed extensions: `pdf` and `docx` only; a filename pattern must end in `.pdf` or `.docx`. Each file is at most 10 MB. The extension and the real content type (detected from file bytes) must both match the pattern's extension. A file name must equal the pattern with `{TEAM}` replaced by the team name, compared case-sensitively (example pattern `{TEAM}_Proposal.pdf` → `CSE4104-7C-T03_Proposal.pdf`). All required documents must be present. A file larger than the upload limit is rejected by the upload middleware with `FILE_TOO_LARGE`.                                                                                                                                                 | API         | `FILENAME_MISMATCH`, `INVALID_FILE_TYPE`, `FILE_TOO_LARGE`                                                                                              |
| BR-16 | **Status derivation.** Submission status is derived by one function `recomputeSubmissionStatus` (see `06-data-model.md` Section 6) and nowhere else. A submission is created only after validation passed, so its initial status is `checked`. Order: grade `published` → `published`; grade `approved` → `graded`; a completed, non-dismissed AI report exists → `ai_reviewed`; else `checked`.                                                                                                                                                                                                                                                                                                                                                                                                                | API         | –                                                                                                                                                       |
| BR-17 | **Late flag.** `submissions.is_late` is set once, at creation, by BR-12. It never changes.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | API         | –                                                                                                                                                       |

## 4. GitHub and contribution data

| ID    | Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | Enforced at | Error code                                                                  |
| ----- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- | --------------------------------------------------------------------------- |
| BR-18 | **Commit attribution.** A commit is assigned to a member by this order: (1) the commit's GitHub author login equals the member's `github_username` (case-insensitive); (2) the commit author email equals the member's registered email (case-insensitive); (3) the commit author email is a GitHub noreply address of the form `{id}+{username}@users.noreply.github.com` or `{username}@users.noreply.github.com` with `username` equal to the member's `github_username`. Otherwise the commit is `Unassigned`.                                                                                  | API         | –                                                                           |
| BR-19 | **Contribution interpretation.** Metrics are calculated from commit metadata only. The system and its UI never describe commit count, lines changed or activity share as a definitive measure of individual effort or quality. The mandatory disclaimer text is in `10-ui-routes-and-text.md` Section 3. The system does not generate automatic risk flags or risk thresholds; the Instructor interprets the data.                                                                                                                                                                                  | UI, API     | –                                                                           |
| BR-20 | **GitHub scope.** Only public repositories on `github.com` are supported. The URL must match `^https://github\.com/([A-Za-z0-9_.-]+)/([A-Za-z0-9_.-]+?)(\.git)?/?$`. "Public" is checked from the GitHub API response (`private` is false), not assumed from the token's access. The system uses read-only access and never writes to GitHub.                                                                                                                                                                                                                                                       | API         | `INVALID_REPOSITORY_URL`, `REPOSITORY_UNREACHABLE`, `GITHUB_REPO_NOT_FOUND` |
| BR-21 | **Sync policy.** A manual sync for a team is refused with `SYNC_COOLDOWN` if the team's last sync finished less than 5 minutes ago. A submission-triggered sync ignores the cooldown. Only one sync per team may run at a time (`SYNC_IN_PROGRESS`). A sync lists commits only from the offering `start_date` onward, keeps the newest 2,000 distinct commits across all branches, and sets `truncated = true` if more exist. Commits are stored in batches, so a sync that fails (for example on a rate limit) keeps its progress, and the next sync fetches details only for SHAs not yet stored. | API         | `SYNC_COOLDOWN`, `SYNC_IN_PROGRESS`                                         |
| BR-22 | **Analysis period.** For a milestone, `periodStart` = deadline of the **published** milestone with the next lower `weekNumber` in the offering, otherwise the offering `start_date` at 00:00 Asia/Dhaka. `periodEnd` = the milestone deadline, or the submission's `submitted_at` if the submission exists and is later. Without a milestone (all-time view) the period is the offering `start_date` at 00:00 Asia/Dhaka until now.                                                                                                                                                                 | API         | –                                                                           |
| BR-23 | **Counted commits.** "Counted" commits are stored commits whose `authored_at` is inside the period and that are not excluded. Merge commits (more than one parent) are excluded when `exclude_merge_commits` is true (default). Bot commits (author login ending in `[bot]` or GitHub user type `Bot`) are excluded when `exclude_bot_commits` is true (default). Excluded commits remain stored. A member's `sharePercent` is that member's counted commits divided by all counted commits of the team, including Unassigned ones.                                                                 | API         | –                                                                           |

## 5. AI review

| ID    | Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    | Enforced at | Error code                                                |
| ----- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- | --------------------------------------------------------- |
| BR-24 | **Anonymisation.** Before any request to Gemini, member names, GitHub usernames and email addresses are replaced by labels (`Member A`, `Member B`, ...). Unmatched authors are labelled `Unassigned Author 1`, `Unassigned Author 2`, ... Any occurrence of a member's full name, GitHub username or email inside a commit message is replaced by that member's label. Commit messages and milestone guidelines are also sanitised (first line only, URLs, emails and path-like text removed). Source code, file contents, file paths, diffs, repository URLs and team names are never sent. Only the fields listed in `09-ai-integration-spec.md` Section 3 are sent. | API         | –                                                         |
| BR-25 | **Evidence validity.** An AI-generated flag is kept only if it cites at least one commit reference and every cited reference exists in the input that was sent for that report. Flags that fail are dropped and counted in `result.droppedFlagCount`.                                                                                                                                                                                                                                                                                                                                                                                                                   | API         | –                                                         |
| BR-26 | **AI is advisory.** AI output is a draft. It can never create, change, approve or publish a grade, and can never change a submission status except `ai_reviewed` through BR-16.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         | API         | –                                                         |
| BR-27 | **AI generation limits.** Only an Instructor can request a review. It requires at least one counted commit in the period (else `NO_COMMIT_DATA`). One review may be pending per submission (`AI_REVIEW_IN_PROGRESS`). At most 10 review requests per Instructor per hour (`RATE_LIMITED`). At most 400 commits are sent (the newest 400 in the period). The prompt version is fixed in code (`v1.0`).                                                                                                                                                                                                                                                                   | API         | `NO_COMMIT_DATA`, `AI_REVIEW_IN_PROGRESS`, `RATE_LIMITED` |

## 6. Grading and visibility

| ID    | Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | Enforced at | Error code                                    |
| ----- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- | --------------------------------------------- |
| BR-28 | **Grade authority.** Only an Instructor can enter or edit rubric scores and feedback, approve a grade and publish it.                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | API         | `FORBIDDEN`                                   |
| BR-29 | **Grade and status visibility.** Students and Team Leaders see a grade and feedback only when the grade status is `published`. Draft, approved-but-unpublished grades and all AI content are visible to Instructors only. Students never see AI reports or AI flags. Because the stored statuses `ai_reviewed` and `graded` would reveal AI or grading activity, every API response to a student or Team Leader shows a **student status** instead: `submitted` for stored `checked`, `ai_reviewed` or `graded`, and `published` for stored `published`. Instructors always see the stored status. | API         | –                                             |
| BR-30 | **Grade arithmetic.** Each score is between 0 and the criterion `maxPoints`, with at most 2 decimals. `totalScore` = sum of criterion scores. Approval requires every criterion to have a score and feedback text of at least 10 characters.                                                                                                                                                                                                                                                                                                                                                       | API         | `GRADE_INCOMPLETE`, `VALIDATION_ERROR`        |
| BR-31 | **Grade lifecycle.** `draft` → `approved` → `published`. Allowed transitions: save (stays `draft`); approve (`draft` → `approved`); publish (`approved` → `published`); unpublish (`published` → `approved`); editing an `approved` grade returns it to `draft`. A `published` grade cannot be edited; unpublish first.                                                                                                                                                                                                                                                                            | API         | `GRADE_PUBLISHED`, `INVALID_GRADE_TRANSITION` |
| BR-32 | **Team data isolation.** A student or Team Leader can access data of their own team only. An Instructor has read access to all teams (including GitHub data, submissions and metrics) but cannot modify teams.                                                                                                                                                                                                                                                                                                                                                                                     | API         | `NOT_TEAM_MEMBER`                             |

## 7. Accounts and security

| ID    | Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                      | Enforced at | Error code                                                                     |
| ----- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- | ------------------------------------------------------------------------------ |
| BR-33 | **Account fields.** Student ID: exactly 11 digits. GitHub username: 1–39 characters, letters, digits and hyphens, not starting with a hyphen. Email: valid format, max 254 characters, unique case-insensitively. Full name: 2–100 characters. Password: 8–72 characters with at least one letter and one digit.                                                                                                                                          | API, DB     | `VALIDATION_ERROR`, `EMAIL_TAKEN`, `STUDENT_ID_TAKEN`, `GITHUB_USERNAME_TAKEN` |
| BR-34 | **Role assignment and password reset.** Self-registration always creates role `student`. Instructor accounts are created only by the seed script or by an existing Instructor. A user's role never changes. Because there is no email reset, an Instructor can set a new password for a student account (the student is told the new password outside the system and can change it afterwards). An Instructor cannot reset another Instructor's password. | API         | `FORBIDDEN`, `STUDENT_NOT_FOUND`                                               |
| BR-35 | **Registration code.** If the course offering has a non-empty `registration_code`, registration requires the same code (exact, case-sensitive).                                                                                                                                                                                                                                                                                                           | API         | `INVALID_REGISTRATION_CODE`                                                    |

## 8. Reliability, time and data

| ID    | Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | Enforced at | Error code                              |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- | --------------------------------------- |
| BR-36 | **External service failure.** Failure or rate limiting of GitHub or Gemini never deletes stored data and never blocks unrelated features. The failure is recorded on the sync run or AI report and shown to the user.                                                                                                                                                                                                                                                                                                                                         | API         | `GITHUB_RATE_LIMITED`, `AI_UNAVAILABLE` |
| BR-37 | **Time.** Store UTC; calculate days and weeks in Asia/Dhaka; weeks start on Monday.                                                                                                                                                                                                                                                                                                                                                                                                                                                                           | API         | –                                       |
| BR-38 | **Data retention.** Data is kept until the Instructor runs the purge script (`npm run purge:offering`, see `08-architecture-and-project-structure.md`). The system stores commit author names and emails only for repositories registered by teams.                                                                                                                                                                                                                                                                                                           | API         | –                                       |
| BR-39 | **Background processing and recovery.** GitHub sync and AI review run asynchronously in the single backend process. Their state is stored in the database (`github_sync_runs.status` = `queued`/`running`, `ai_reports.status` = `pending`) and the UI polls. Submission validation is **not** asynchronous (BR-14). Because only one backend process runs, every sync run in `queued` or `running` and every AI report in `pending` at server start is orphaned: on start, all of them are set to `failed` with error code `INTERRUPTED`, regardless of age. | API         | –                                       |

## 9. Numeric limits (single source of truth)

Other documents repeat these numbers for convenience. If a number differs, this table wins.

| Limit                             | Value                                    |
| --------------------------------- | ---------------------------------------- |
| Maximum file size                 | 10 MB (10,485,760 bytes)                 |
| Allowed document types            | `pdf`, `docx`                            |
| Signed download URL lifetime      | 60 seconds                               |
| JWT lifetime                      | 8 hours                                  |
| Submission notes                  | at most 2,000 characters                 |
| JSON request body                 | at most 100 KB                           |
| Manual sync cooldown              | 5 minutes                                |
| Commits stored per sync           | newest 2,000 (since offering start date) |
| Commits sent to AI per review     | newest 400 in the period                 |
| AI review requests per Instructor | 10 per hour                              |
| Teams per section                 | 99                                       |
| Team size                         | min 1 to max 10 (defaults 2 and 6)       |
| Weeks                             | 1 to 14                                  |
| Pagination                        | default 20, maximum 100                  |
| Polling interval (UI)             | 3 seconds                                |
