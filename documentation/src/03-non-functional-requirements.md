# 03 – Non-Functional Requirements

Every NFR has a **measurable target** and a **verification method** so it can be tested. Targets are kept realistic for a student project: the critical flows are tested, everything else is reviewed or checked by hand.

Verification methods: **Test** = automated test, **Manual** = checked by hand against a checklist, **Review** = code or configuration review, **Tool** = measured with a named tool.

Phase: 1 = needed for the MVP, 2 = built after Phase 1.

## 4.2 Security (SEC)

| ID         | Requirement       | Target                                                                                                                                                                                                                                                                                                                                                | Verification  | Ph  |
| ---------- | ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------- | --- |
| NFR-SEC-01 | Transport         | HTTPS only in production; HSTS header via `helmet`                                                                                                                                                                                                                                                                                                    | Review        | 1   |
| NFR-SEC-02 | Password hashing  | `bcryptjs`, cost 10 (`BCRYPT_ROUNDS`)                                                                                                                                                                                                                                                                                                                 | Test          | 1   |
| NFR-SEC-03 | Tokens            | JWT HS256, expiry 8 hours, secret of at least 32 random characters                                                                                                                                                                                                                                                                                    | Test + Review | 1   |
| NFR-SEC-04 | Authorisation     | Every route requires authentication and has a role and ownership guard. Tests prove the critical cases: a student cannot call Instructor routes, a non-leader cannot change a team or submit, an Instructor cannot change a team or submit, and a student cannot read another team's data                                                             | Test          | 1   |
| NFR-SEC-05 | Secrets           | All keys only in environment variables; `.env` is git-ignored; `.env.example` has names only; no secret is ever sent to the browser or logged                                                                                                                                                                                                         | Review        | 1   |
| NFR-SEC-06 | Injection and XSS | All inputs validated with zod; all SQL uses parameterised queries (`$1, $2`); React escapes output; no `dangerouslySetInnerHTML` anywhere                                                                                                                                                                                                             | Review        | 1   |
| NFR-SEC-07 | Request hardening | CORS allows only `FRONTEND_ORIGIN`; `helmet` enabled; JSON body limit 100 KB; upload limit 10 MB per file                                                                                                                                                                                                                                             | Test + Review | 1   |
| NFR-SEC-08 | SSRF              | The live-URL reachability checker accepts only `http`/`https` on ports 80 and 443 and refuses private, loopback and link-local addresses, including after redirects. Known limitation: DNS rebinding between lookup and request is not fully prevented. Until this is built, only the URL format is checked and no request is made to a submitted URL | Test          | 2   |
| NFR-SEC-09 | Upload safety     | File type decided from the file bytes (`file-type`), not from the name or the client MIME header; only `pdf` and `docx` accepted; files stored in a private Supabase bucket; names sanitised; no file is ever executed or served inline                                                                                                               | Test + Review | 1   |
| NFR-SEC-10 | Error leakage     | Production error responses never contain stack traces, SQL or secrets; unknown errors return `INTERNAL_ERROR`                                                                                                                                                                                                                                         | Test          | 1   |

## 4.3 Privacy and Data Protection (PRIV)

| ID          | Requirement          | Target                                                                                                                                                                                                                                                                                                    | Verification | Ph  |
| ----------- | -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------ | --- |
| NFR-PRIV-01 | AI data minimisation | The request body to Gemini contains only the approved anonymised fields; an automated test uses a fixture whose commit messages and milestone guidelines contain a member name, username, email, repository URL, team name and file path, and asserts that none of them appears in the serialised request | Test         | 1   |
| NFR-PRIV-02 | Data isolation       | A student or Team Leader can reach only their own team's data; verified by tests for the team-scoped endpoints, including that a student never receives `aiReviews`, an unpublished grade or the stored statuses `ai_reviewed` and `graded`                                                               | Test         | 1   |
| NFR-PRIV-03 | Logging              | Logs never contain passwords, tokens, API keys, email addresses or commit messages                                                                                                                                                                                                                        | Review       | 1   |

## 4.5 Reliability (REL)

| ID         | Requirement      | Target                                                                                                                                                                                                                                                                                                                                                                                        | Verification              | Ph  |
| ---------- | ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------- | --- |
| NFR-REL-01 | Degradation      | If GitHub or Gemini fails, stored data is kept, all other features keep working and the UI shows a clear message                                                                                                                                                                                                                                                                              | Test with mocked failures | 1   |
| NFR-REL-02 | Backups          | Supabase daily backups enabled; before demo day the team takes a manual dump (`pg_dump`)                                                                                                                                                                                                                                                                                                      | Manual                    | 1   |
| NFR-REL-03 | Interrupted jobs | On server start, every sync run in `queued` or `running` and every AI report in `pending` is set to `failed` with code `INTERRUPTED`, regardless of age                                                                                                                                                                                                                                       | Test                      | 1   |
| NFR-REL-04 | Transactions     | Multi-table writes (team creation including team number assignment, submission rows, grade save and publish, leader transfer) run in one database transaction. No transaction stays open during a network call: GitHub checks happen before team creation, and files are uploaded to storage before the submission transaction starts (uploaded objects are deleted if the transaction fails) | Review                    | 1   |
